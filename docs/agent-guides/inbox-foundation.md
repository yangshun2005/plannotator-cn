## Plannotator Inbox

每台机器一个长期运行的本地服务器。Agent 把消息、`:::question` 块、文件和引导式审查留在那里给用户，用户有空时再回复。它不会让任何 agent 会话保持打开。回复通过 Claude Code、Pi 或 OpenCode 连接唤醒发起提问的会话；其他 agent 之后用 `read_thread` 读取。窗口的设计记录和所有者的决策私下保存（不在本仓库中）；本节只包含此处构建所需的内容。未构建：Mac 通知辅助程序（目前只有原型）。面向用户和 agent 的文档位置：`plannotator --help`（`apps/hook/server/cli.ts`）和 agent 指南 `plannotator inbox --help`（`apps/hook/server/inbox-help.ts`，见"命令"），`plannotator` 技能的 `## plannotator inbox` 部分（`apps/skills/core/plannotator/SKILL.md`；刻意简短：用法行、何时使用 Inbox、工具还是 MCP，以及先阅读 `plannotator inbox --help` 的指引，因此细节在指南中而非技能中），以及营销参考页 `apps/marketing/src/content/docs/reference/inbox.md`（`/docs/reference/inbox/`）。命令、MCP 工具列表或开关的变更会更新指南和参考页，技能仅在其用法行或何时使用规则变化时更新。

**命令**（`apps/hook/server/inbox-command.ts`，用法在 `cli.ts`，agent 指南在 `inbox-help.ts`）。
- `plannotator inbox` 在前台启动 Inbox 并在浏览器中打开，或打开正在运行的 Inbox。
- `plannotator inbox --background` 以分离方式启动（独立会话，输出到 `inbox/inbox.log`），打印 URL 并以 0 退出。它从不打开浏览器，因此按需启动永远不会在工作过程中弹出标签页。
- `plannotator inbox --no-open` 在此处运行，不打开浏览器。
- `plannotator inbox --open` 在浏览器中打开 Inbox 并在 stdout 打印其 URL，退出 0：打开正在运行的 Inbox，否则先通过 `--background` 路径启动一个（分离方式，因此从不阻塞调用方；与任何分离启动一样，没有 agent 连接）。浏览器通过 `openBrowserDetached`（`packages/server/browser.ts`）打开：打开器在其自己的进程组中运行，无 stdio，且从不等待，因为打开器启动的浏览器可能在其运行期间一直持有输出（`openBrowser` 会等待，这对裸 `plannotator inbox` 是正确的，保持不变）；VS Code IPC 有 2 秒限制。在远程会话（`isRemoteSession()`）中且未设置浏览器时，只询问 VS Code 的 IPC，从不询问远程主机上的系统打开器，stderr 会输出一行关于 `ssh -L <port>:127.0.0.1:<port>` 或 `--tailscale` 的提示（`inboxRemoteOpenHint`）。它拒绝同时使用 `--background` 和 `--no-open`（退出 1）。每个 `/plannotator-inbox` 命令运行的都是它（用户关闭了标签页，或询问 Inbox 在哪里），agent 指南也告诉 agent 在用户询问其 Inbox 在哪里时运行它。
- `plannotator inbox --open <thread>`（issue #2506；线程 id、消息 id 或 `#thread=` 链接，`inbox-command.ts` 中的 `inboxThreadRef`）通过受令牌保护的 `POST /api/inbox/control/show` 在此计算机上已打开的 Inbox 窗口中显示该线程：用户最后使用的窗口（它最后报告了焦点；从不通过 tailnet 打开的窗口）像点击行一样打开它（新的历史记录条目，因此后退可返回；正在输入的回复保持为草稿）。它打印 `<url>#thread=<id>` 并立即返回；不打开标签页。没有窗口打开时（或旧版 Inbox 没有该路由），它像裸 `--open` 一样在浏览器中打开该地址。未知线程：退出 1，在 stderr 上说明。此计算机上的任何东西都可以运行它（状态栏小部件、脚本、agent）。它不会提升窗口：调用方可以。

- `--tailscale`（与三者中任一一起）还会在本次运行中通过 tailnet 发布它（见"通过你的 tailnet"）；已有 Inbox 运行时，命令通过受令牌保护的 `POST /api/inbox/control/tailscale` 要求它发布。Stdout 仅保留本地 URL；tailnet URL（在 TTY 上带二维码）或未发布的原因输出到 stderr，退出码从不取决于 Tailscale。仅由该标志发布的运行在重启更新时会传递 `--tailscale`。
- `plannotator inbox mcp` 是 stdio MCP 入口（`apps/hook/server/inbox-mcp-shim.ts`），一个轻量 JSON-RPC 代理：
  - 它将每条 stdin 消息 POST 到 Inbox 的 `/mcp`，并将每个答案写入 stdout。
  - 它在每条消息上重新读取 `inbox/inbox.json`，并通过 `--background` 路径启动已停止的 Inbox（不打开标签页）。
  - 当 agent 省略它们时，它填充 `project_path`（其工作文件夹，或 `PLANNOTATOR_CWD`；在 Claude Code 或 Pi 会话内，为该会话的项目，来自 `PLANNOTATOR_SESSION_PROJECT`，见"会话的项目"）和 `agent_session`。
  - 当 shim 在 agent 主机内运行时，会话是 agent 主机自己的（`inboxHostSessionFromEnv`）：格式良好的 `PLANNOTATOR_SESSION_TAG`（`<host>:<id>`，主机为 `claude-code`、`pi` 或 `opencode`，id 为 `[A-Za-z0-9][A-Za-z0-9._-]{0,127}`；其他任何内容被忽略），否则是 T3 Code 的 `T3CODE_THREAD_ID`（T3 给线程的任何 id，为 Claude T3 运行设置；`agent_host: "t3"`，见 `inbox-notifications-and-agents.md` 中的"T3 Code"），否则是 Pi 自己的 `PI_SESSION_ID`（Pi 在每次 bash 工具调用时设置），否则是 Codex 的 `CODEX_THREAD_ID`（Codex 在其 shell 运行的命令中设置；一个 UUID，其他任何内容被忽略），否则是 Qwen Code 的（见下文），否则是 Muse Code 的 `MUSE_SESSION_ID`（Muse 将其传递给其启动的每个 stdio MCP 服务器；上述形状的任何 id；`agent_host: "muse"`，名称为"Muse Code"；没有东西唤醒它，见 `inbox-notifications-and-agents.md` 中的"Muse Code"）。来自 Codex 本身的工具调用属于其线程，无论环境说什么：当 MCP 客户端是 Codex（`initialize` 的 `clientInfo.name` 为 `codex-mcp-client`，或调用携带 Codex 的 `x-codex-turn-metadata`）且调用命名了线程 id（`params._meta.threadId`，Codex 在每个工具调用上放置），shim 以 `agent_host: "codex"`、`agent_session: <thread id>`、`agent_name: "Codex"` 发送（`codexThreadOfCall`，`packages/core/inbox-codex.ts`），并在调用上保留 `_meta`（见"Agent 连接和开关"下的"Codex 唤醒"）。仅当 agent 未命名 `agent_host` 或同一主机时才采用主机会话（在 T3 线程中，`claude-code` 也是：那里的 Claude 可能这样命名自己）；命名另一主机的 agent 得到 shim 自己的 `ses_` id，因此对其的回复永远不会唤醒会话。在 `send_message` 和 `submit_guide` 上，它还会填充 `agent_host` 和 `agent_name`（`Claude Code`、`Pi`、`OpenCode`；仅当 agent 未给出名称时），因此作者与该主机的 `plannotator_inbox` 工具写入的逐字节相同。因此，Claude Code 或 Pi 会话运行的脚本或命令以该会话发送：相同的作者，`asked_by: "me"` 看到该工具的线程，用户的回复通过其连接唤醒会话（`pendingReplies` 匹配 `author.session`）。agent 传递的 `agent_session` 总是优先。从 agent 的 shell 启动的长期运行进程（tmux、nohup）继承的标签继续命名该会话；显式传递 `agent_session` 以覆盖。

  - Qwen Code（`inboxCallHostSession`，在每次工具调用时读取；纯部分在 `packages/core/inbox-qwen.ts`，注册表读取在 `packages/shared/inbox/qwen-sessions.ts`）。Qwen 在其启动的进程中设置 `QWEN_CODE_SESSION_ID`，但 `/clear` 和 `/resume` 在同一进程下给会话一个新 id，而 MCP 服务器保留旧的，因此 shim 每次询问 Qwen 自己的会话注册表：`$QWEN_HOME/sessions/<parent pid>.json`（否则父进程的单个 `<pid>-<8 hex>.json`；两个或更多：只有调用能说明），按 Qwen 协议所述检查（schema 版本 1，`pid` 等于文件名，UUID 会话 id；形状错误的 `kind` 读作 `tui`，如 Qwen 读取），从不写入。顺序：守护进程运行的会话自己的 `_meta["qwen-code/invocation"].sessionId` 在调用上；然后，当调用方是 Qwen 时（`clientInfo.name` 为 `qwen-cli-mcp-client-<server name>`，或较旧的 `qwen-code-mcp-client`；或父进程的注册表记录），记录的 id，否则变量；仅变量仅在无其他客户端命名自己时计数（MCP 客户端的进程可能从 Qwen shell 继承它）且在另一主机自己的变量（`PLANNOTATOR_SESSION_TAG`、`PI_SESSION_ID`、`CODEX_THREAD_ID`）之后。`inboxHostSessionFromEnv` 最后取变量，因此 Qwen 的 shell 运行的命令（`plannotator card`）也以该会话发送。作者是 `agent_host: "qwen"`、`agent_name: "Qwen Code"`。用户的回复自行进入正在运行的 Qwen Code 会话（Qwen 唤醒，inbox-notifications-and-agents.md）；命名 `qwen` 的 `PLANNOTATOR_SESSION_TAG` 必须携带 Qwen 会话 id。
  - 否则每个 shim 进程一个 `ses_` id，因此 MCP 客户端的身份随其 MCP 服务器进程结束；希望线程跨重启的客户端自行传递 `agent_session`。对已结束会话的回复从不交给另一会话。
  - OpenCode 不向其运行的命令导出会话变量（OpenCode 2 的 `shell.create.before` hook 不携带会话 id；OpenCode 1 的 `shell.env` 有但 OpenCode 1 没有唤醒），因此那里的命令仍得到新 id（除了 `plannotator inbox call`，它得到 Tidy 的 `--session` 或无 id）。
- `plannotator inbox call [--session <id>] <action> [<json> | -]`（`apps/hook/server/inbox-call-command.ts`，批准"inbox-scripting-command"）从脚本运行一个 Inbox 工具操作，因此 agent 可以一次完成整个整理，而不是每个修复一次工具调用、一个结果在其上下文中。
  - 轻量客户端：对运行中 Inbox 的 `/mcp` 一次 `tools/call`，由 shim 自己的 `fillInboxToolArguments` 填充，没有自己的发送、读取或卡片逻辑。`/mcp` 的边界不变：仅 `127.0.0.1`，从不浏览器、tailnet 或链接的机器。已停止的 Inbox 通过 `--background` 路径启动
