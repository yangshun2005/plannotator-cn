## 收件箱：手机与安全

**在手机上**：`adr/implementation/inbox-mobile.md` 是 iPhone 应用及其服务端步骤所依据的通信契约：配对邀请、设备令牌入口 `/api/inbox/device/*`、局域网监听器、中继、界面桥接以及幂等规则。已构建（P1、P2、R1、R2、R3）：配对、入口、tailnet 路径、局域网监听器，以及中继的邮箱、推送（APNs，Android 用 FCM：第 10 节）和承载。Plannotator iPhone 应用位于 Workspaces 仓库。删除线程时收件箱不写入事件：手机在该线程的下一次读取时才会得知。未构建：1.3 中的 Bonjour 发现（移动的 Wi-Fi 地址只能通过重新扫描代码来跟踪）。

**手机浏览器中的窗口**（所有者通过 tailnet 访问的页面；不是 iPhone 应用）：一次一屏（`packages/inbox/phone.ts`：`PHONE_QUERY`、`usePhone` 和 `trackKeyboard`，后者通过 `--ib-vvh`、`--ib-kbd-inset` 和 iOS 固定跟随可视视口中的键盘）。其编辑器（回复框和"新消息"合为一张浮动卡片，行内的 agent 控件及其底部弹层）见 [`inbox-compose.md`](inbox-compose.md) 中的"手机编辑器和其选择器弹层"。

**手机**（`packages/server/inbox-devices.ts`，记录在 `packages/shared/inbox/devices.ts`；契约第 1、2、6 节）。
- 除非收件箱启动时设置了 `PLANNOTATOR_INBOX_PHONES=1`（或 config.json 中 `inboxPhones: true`），否则关闭：在 iPhone 应用发布之前，已发布的收件箱没有配对、没有入口、没有可达开关、没有中继、没有"手机"区块，所有这些路由都返回未知路由 404（见环境变量表）。唯一例外是已关联的机器（[`inbox-machines.md`](inbox-machines.md)）：手机功能关闭时，入口仍会响应已关联机器的令牌、机器邀请开放期间的 `pair`，以及通过 tailnet 监听器或机器配对后对未知令牌返回 `401 device_token_invalid`；对其他任何请求仍是 404。tailnet 入口仅在机器已关联时发布（或邀请开放中，或未关联机器仍待拒绝；见 inbox-machines.md）。在最后一次到达对方机器的取消关联后关闭；若未能到达，则保持最多一周，直到该机器被拒绝一次。机器从不通过 Wi-Fi 监听器配对或连接。以下内容均描述开关打开时的收件箱。
- 配对：设置中的"配对手机"调用 `POST /api/inbox/pairing`，打开一个邀请：一个 `plannotator://pair` 链接（用 `uqr` 绘制为二维码，`packages/inbox/qr.ts`），携带计算机名称、tailnet 开启时的 tailnet 地址、Wi-Fi 开启时的局域网地址和证书 SHA-256（`lan`、`fp`）、32 字节密钥和六位数字。同一时间只有一个邀请开放，仅存于内存。它在被兑换、窗口生成另一个、创建后 10 分钟、或 5 次错误代码后关闭：这是配对所需的两个限制，也是仅有的两个。手机在 `POST /api/inbox/device/pair` 用密钥或数字兑换自己的 `tok_` bearer 令牌，仅返回一次。
- `inbox/` 下的记录：`devices.jsonl`（存储的行规则；`dev_` id、名称、平台、令牌的 SHA-256 而非令牌本身、创建时间、最后出现时间、撤销时间、`carriage`）、`device-secrets/<dev id>`（配对密钥，位于 0700 文件夹中的 0600 文件，用于中继的密钥；撤销时删除）和 `device-commands.jsonl`（入口按 key 的应答）。最后出现时间在每次请求时存于内存，在其 UTC 日期变化时写入。
- 中继（`packages/server/inbox-relay.ts`；Worker 在 `apps/relay`；契约第 4 节）：
  - 首次配对创建邮箱（`POST /v1/mailboxes`，携带新生成的 32 字节邮箱密钥的 SHA-256），并保存在 `inbox/relay.json`（0600）：`{ v: 1, url, mailbox_id, secret }`。兑换的应答携带 `relay: { url, mailbox_id }`，中继不可达时为 null（调用最多等待 10 秒）。每部已配对手机用其 relay 密钥的 SHA-256 注册（由其配对密钥经 HKDF 派生，`packages/core/crypto.ts` 中的 `deriveRelayKeys`），撤销时从中继移除。
  - 手机配对期间保持一条到邮箱的出站 WebSocket，重连间隔 1 秒到 60 秒。`hello` 将每部手机的 relay 开关写入其记录，在中继移除在此撤销的手机，并注册中继未列出的手机；`carriage` 写入手机翻转的开关。手机用其 relay 密钥在中继自行注册推送令牌：APNs（iPhone）或 FCM（Android，第 10 节），每设备一个。
  - 承载（R2）。帧按到达顺序逐个处理。下行：`hello` 之后，每部开关打开的手机获得中继为其保存的游标之后的所有存储行（`changesSince`，与事件流追赶一致），然后每写入一行即发送一行，作为 `item` 用手机密钥 `K` 密封（事件流的 `record` 载荷加上 `v`、`type` 和 `after`，即上一项到达的 seq，以便手机察觉缺口）；超过 Cloudflare 32 MiB WebSocket 消息的行作为 `too_large` 占位符下行，游标越过它。推送明文携带 `type: "push"`，因此两者不能互相冒充。上行：每个 `command` 用手机的上行密钥 `U` 打开（每方向一个密钥，因此反射上行的下行信封无法打开），在进程内通过入口以该设备身份应用（`inbox-devices.ts` 中的 `asDevice`：撤销检查、允许列表和幂等日志，绝不使用回环 HTTP 调用），以密封在其中的 id 下的 `result` 项应答（密封 id 不是中继的帧 id 则拒绝），状态、类型和响应体字节以 base64 表示（文件是 GET 结果；超过 Cloudflare 32 MiB WebSocket 消息 3/4 的响应体，即 base64 增长后，替换为 413 `result_too_large`，在读取任何字节前根据 Content-Length 拒绝，无 Content-Length 的响应体只读取到超过该界限为止，`readRelayBody`），并报告 `applied`。`pair` 和 `events` 不承载。v1 中密封命令不携带头部，因此没有 Range 能通过中继到达窗口：视频的 `video` 或 `download` 返回整个文件，能装入一帧时承载，否则返回 `413 result_too_large`；手机通过 Wi-Fi 或 tailnet 播放视频（8 MiB 或更小的中继范围是 v1.1，`adr/implementation/inbox-mobile.md` 契约第 3 节）。没有密钥能打开的命令报告为已应用，无结果。收件箱停止时，命令在中继等待，下次启动时应用；重放返回存储的结果，不写入任何内容。
  - 推送：agent 的消息落地时带有问题或引导式审查，或取代了先前的问题（被替换的问题；然后 `question: null`，除非它提出新问题），（其在存储中的第一行）向每部开关打开的已配对手机发送一次推送，摘要（线程、主题、项目、agent，以及一个最多四个选项的单选问题）用 `encryptWithKey` 以该手机的密钥密封，按线程用该密钥下线程 id 的 HMAC 折叠（中继永远看不到线程 id）。超过 Apple 的 4096 字节时，先丢弃问题的上下文，再丢弃问题，然后仅发送 id。
  - 中继为 `https://relay.plannotator.ai`（尚未部署；在此之前配对返回 `relay: null`），除非 `PLANNOTATOR_RELAY_URL` 指定其他地址。已配对的云 agent 在手机功能关闭时使用同一中继（契约第 13 节）：收件箱仅在其应答期间配对过云 agent 后才访问它。测试从不访问托管中继：根预加载和测试环境将其指向一个关闭的回环端口。
  - Worker（`apps/relay`）：每个邮箱在 SQLite 上一个 Durable Object（`mailbox` 含密钥哈希；`devices` 含 relay 密钥哈希、开关、游标、APNs 令牌和环境或 FCM 令牌、下一项编号；`items` 和 `commands`，信封按 1,000,000 字符分块保存，因为一行不得超过 2 MB）。下行项在手机确认时删除（按项编号，或直接读取时按存储游标），并在其关闭开关时删除；命令在收件箱报告已应用时删除；设备被移除时其持有的所有内容删除。一个设备持有一个推送令牌，APNs 或 FCM（`PUT .../apns` 和 `PUT .../fcm` 各自清除另一个；`hello` 按设备列出 `apns` 和 `fcm`），推送发往其持有的那个；两者皆无时返回 `no_push_token`（R3 前为 `no_apns_token`；收件箱仅记录原因）。APNs 通过 `connect()` 走 HTTP/2（`src/apns-h2.ts`；Worker 的 `fetch` 无法到达 APNs；它拒绝超过 16 KiB 的帧，最多保留应答的 8 KiB），ES256 提供者令牌来自 `APNS_KEY` 密钥，保留 50 分钟；410 删除令牌；无密钥时推送返回 `no_apns_key`。FCM（R3，`src/fcm.ts`）：HTTP v1 `messages:send` 使用普通 `fetch`，仅含 body 数据（`{ message: { token, data: { e }, android: { priority: "high", collapse_key } } }`），OAuth 访问令牌由 `FCM_SERVICE_ACCOUNT` 密钥铸造（服务账号的 JSON 密钥文件：用 WebCrypto 签名的 RS256 JWT，在 oauth2.googleapis.com 交换），保留 50 分钟；`UNREGISTERED` 删除令牌（`fcm_gone`）；其他任何拒绝为 `502 fcm_failed`，附带 `fcm_status` 和 `fcm_reason`；无密钥时推送返回 `no_fcm_key`。大小阶梯仍以 APNs 响应体衡量，围绕同一信封它总是大于 FCM 的数据载荷。邮箱创建采用 guides.show 的速率限制规则（每 IP 每分钟 20 次）：先速率限制绑定（按机器近似并缓存，因此单独它就让不同连接上的请求通过），然后硬计数，每客户端地址一个 `CreateBrake` Durable Object（`src/create-brake.ts`，迁移 `v2`；一行，60 秒窗口的开始和计数，窗口结束时由闹钟删除）；在回环之外任一缺失或失败返回 `503 brake_unavailable`（`src/brake.ts`，在 `test/limits.test.ts` 中测试）；其他均不限速（推送不限：推送需要手机的推送令牌，只有应用和中继持有）；不按时间清扫。仅用于证明的主机覆盖（`APNS_ORIGIN`、`FCM_ORIGIN`、`FCM_OAUTH_ORIGIN`、`src/origin.ts`）仅对回环主机生效；其他任何值被忽略并记录一行日志，因此没有签名令牌流向别处。并发 FCM 推送共享一次令牌交换，被拒绝的交换（或不可读的私钥）在一分钟内从内存应答。
