# 评估：本地堆叠父分支检测（并非承诺构建）

状态：仅评估。决策待定。本文在临时仓库中对该候选算法做了实证压力测试，并在本仓库自身（feat/commit-list 堆叠在 feat/simple-git 上，35 个本地分支噪声）上验证后写成。

## 问题

PR 审查模式从平台*声明的*基础分支获取堆叠感知（pr-stack.ts）。本地会话没有声明的基础分支——git 不会在任何持久位置存储"分支 X 是从分支 Y 创建的"。我们能否在本地检测堆叠父分支，且可靠到足以据此行动？

## 候选算法（"merge-base 可达性"）

对于当前分支 B，默认基础分支为 D（origin/main）：

- 对每个其他分支 P：`mb = merge-base(B, P)`。
  **P 合格当且仅当 `mb` 不是 D 的祖先**——即 B 的历史包含存在于 P 但不存在于 D 的提交。这是"构建于 P 的独有工作之上"的图论真实定义。
- 选择 `mb` 最深的合格分支（越过 D 的提交最多）；平局时按最小尖端距离（`mb..P` 计数）决胜。

## 两类失败并不同等严重

**S5b（标签错误，同一 merge-base）对内容无害。** 每个审查界面都以 `merge-base(base, HEAD)` 为键——自基础分支以来的差异、分区划分、提交面板边界。同一分叉点的合格分支有*相同*的 merge-base，所以选错兄弟分支产生的审查逐字节相同；只有标签在说谎。已验证：S5/S5b 的 mb 相等。

**S6/S6b（子分支陷阱）会静默隐藏工作。** 指向 B 自身历史内部的分支（检查点、review/*、某人从 B 切出的分支）在深度上胜出，其 merge-base 落在 *B 内部*——审查随后排除 B 自身较早的提交，无错误、无视觉提示。这就是会把事情搞砸的情况。

**而且它可证明无法仅靠图查询检测。** "X 在提交 M 处从 B 创建"和"B 在 M 处从 X 创建"产生相同的图；箭头不携带历史。Reflog 也救不了：常见的创建路径（站在父分支上执行 `git checkout -b`）记录的是 `branch: Created from HEAD`——没有父分支名（已实证验证）。Reflog 也仅限本地且会过期。

## 结论

- **堆叠性测试**是确定性的，在任何场景中都从未说谎："B 是否构建于 D 中不存在的提交之上，以及哪个分叉提交"是图论真相。S2/S4/S7 都正确报告*无堆叠*。
- **父分支归属**是一种启发式，有一个无害的失败模式（同 mb 标签，S5b）和一个危险的失败模式（子分支陷阱，S6），后者无法消除，只能缓解。

因此，若要构建，唯一负责任的形态是：

1. **建议，绝不自动应用。** 在本地 git 审查的会话开始时，若存在合格分支："此分支看起来堆叠在 `feat/simple-git` 上——要与之比较吗？"一键通过现有的基础分支切换路径应用。建议必须以数字展示后果（"审查其上方的 7 个提交"）——这样子分支陷阱的误建议就不言自明，因为计数会明显吞掉用户自己的提交。
2. **按仓库+分支持久化用户的明确选择**（config.json），使后续每个会话都是确定性的——检测只用于*提供建议*，绝不用于决定。存储引用名，绝不存储 sha（变基安全），与提交视图已遵循的规则相同。
3. **在提示中展示所有合格分支**（真实仓库中有 2 个），而非单一自信答案。

## 明确拒绝

- 静默自动默认为检测到的父分支（S6 使其不可接受）。
- 基于 reflog 的检测（Created-from-HEAD 缺口；仅限本地；会过期）。
- 信任尖端距离决胜用于建议列表排序之外的任何用途（S5b）。

## 构建前的开放问题

- 仅远程分支（origin/*）是否应作为候选？（队友全新克隆的堆叠没有本地父分支。）
- 缓存/刷新策略：合格分支在每次 fetch/变基时都会变化；建议应在每个会话重新计算，持久化的选择应静默胜出。
- 与 PR 流程的交互：一旦 PR 存在，平台声明的基础分支应取代任何本地推断。
