# 006. 将引导式审查作为一等代码审查功能

日期：2026-07-02

## 状态

已接受

## 背景

大型变更集很难逐文件审查。Linear 的 Guides（测试版）展示了一种更好的形态：由 agent 将 diff 拆分成若干章节，按工作推演的思路排序——核心实现在前，后续影响其次，胶水代码和低信号变更单独分离——每个章节将解释变更*为何*存在的文字说明与相关 diff 配对呈现。

Plannotator 已具备所需的几乎所有基础设施：agent-jobs 引擎（启动 CLI 提供方、SSE 状态/日志流、结构化输出解析）、Code Tour 提供方作为 schema 约束叙事输出的先例、描述任意 diff 模式（PR 或本地）的共享 agent-review 提示词机制、基于 Pierre 的 diff 渲染（`FileDiff` / 虚拟化 `CodeView`），以及单一标注系统（`useAnnotationToolbar` → `CodeAnnotation` → `/api/feedback`），该系统已接受来自多个界面的标注。

## 决策

将**引导式审查**构建为 Plannotator 代码审查应用的一等功能。

1. **引导形态。** 引导是一组有序页面（章节）。每个页面包含：标题、位置指示（"01 / 04"）、勾选后折叠页面的**已审查**复选框、文字概述（变更是什么以及为何存在），以及一个或多个 diff 区块——同一底层审查补丁的真实渲染切片。一个页面可包含一个或多个 diff。

2. **适用于任意变更集。** 引导可为 PR 和本地 diff（基于基线、未提交等）生成。存在 PR 时引导标题取自 PR，否则取自变更本身。

3. **生成是 agent 任务。** 引导由启动的 agent 通过现有 agent-jobs 基础设施生成——相同的启动路径、相同的引擎/模型/投入设置（`useAgentSettings`）、相同的 SSE 生命周期。结构上遵循 Code Tour 提供方：通过共享提示词机制（`agent-review-message.ts`）基于当前 diff 上下文构建 schema 约束的结构化输出。

4. **呈现方式是整屏接管，而非对话框或停靠面板。** 入口是左上角页头中文件树切换按钮旁的"Guide"徽章。点击后替换主工作区：文件树和中央停靠区隐藏；右侧边栏可保留。屏幕是干净、优雅、类似 Notion 的页面。尚无引导时显示空状态——"开始引导式审查？"——附带启动控件和首次使用的模型默认值（与 agent 任务使用相同设置）。

5. **标注对等是硬性约束。** 引导页面内的 diff 使用与普通 diff 视图完全相同的组件和状态进行标注——相同的工具栏/弹出框/建议机制、`App.tsx` 中相同的 `CodeAnnotation` 列表、相同的反馈导出。复用而非复制。在引导中创建的标注与在 diff 视图中创建的标注无法区分，并流入同一 Send Feedback 载荷。

6. **范围校准。** 预期复杂度与 agent-jobs 部分相当，而非新子系统：新的任务提供方 + 输出 schema、引导数据模型、接管屏幕，以及现有组件的组合。

有意推迟（在规格/规划阶段确定，不改变本决策）：引导在服务器内存之外的持久化（Tour 仅存于内存；引导可能需要持久化）、单活动引导 vs. 每会话多引导，以及引导 diff 切片锚定回真实补丁的粒度（文件级 vs. hunk 级）。

## 后果

- 审查应用获得第二种主要阅读模式：现有文件/diff 工作区和引导接管屏幕，从页头切换。布局代码必须支持隐藏文件树和中央停靠区，同时保持标注和侧边栏状态活跃。
- 新的 agent-job 提供方（guide）加入 `claude`/`codex`/`tour`/marker 引擎，拥有自己的系统提示词、输出 schema、解析器和结果存储——遵循 Tour 模式（`packages/server/tour/`），而非发明新生命周期。
- 标注系统必须可从第二个渲染界面消费而不重复；`useAnnotationToolbar`/`DiffViewer` 内部与停靠区布局的任何耦合都应被抽离而非复制。
- 引导的"已审查"复选框状态需要类似 Tour 清单的存储（`PUT /api/tour/:jobId/checklist` 先例）。
- 提示词和 schema 质量决定功能价值：按语义重要性分节（核心在前，胶水在后）就是产品本身，因此引导提示词需获得与 `TOUR_REVIEW_PROMPT` 同等程度的打磨。
