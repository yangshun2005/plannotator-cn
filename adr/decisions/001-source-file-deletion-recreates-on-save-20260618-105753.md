# 001. 保存时重建已删除的源文件

日期：2026-06-18

## 状态

已接受

## 背景

Plannotator 可在标注会话中编辑本地源文件。它监听磁盘变更，以便编辑器更新干净文件、在脏冲突时警告，并避免发送过期的已保存编辑上下文。

一次审查发现，当被监听的文件在 Plannotator 外部被删除或重命名时，磁盘同步路径会把缺失文件折叠为无操作。这导致最后加载的编辑器文本和任何 Edits 上下文看起来仍是最新的，尽管文件已不在原路径。

我们曾考虑将删除视为特殊的恢复流程，提供重建、丢弃或重新加载等选项。这比所需更重。期望行为更接近 VS Code：保留打开的编辑器内容，通知用户原文件已消失，并让保存将当前内容写回同一路径。

## 决策

当源文件在磁盘上缺失时，Plannotator 将保持内存中的编辑器内容打开且可见，并通知用户该文件已不在其路径。

保存仍然可用。若用户保存，Plannotator 将在同一路径以当前编辑器内容重建文件，并恢复正常源文件保存跟踪。

缺失不等于不可用。确认缺失的文件可更新文档状态，并清除或标记该路径的已保存编辑上下文为过期。短暂的不可用读取不得破坏性地清除状态。

Plannotator 不会为此情况添加单独的重建/丢弃模态框。关闭或丢弃打开的文档会丢弃内存副本。没有磁盘文件可重新加载时，不提供重新加载。

缺失文件的已保存 Edits 上下文不得被当作仍描述当前磁盘文件发送。反馈提交在发送前仍会校验源文件上下文。

外部文本变更继续遵循现有冲突策略：若用户无未保存编辑，Plannotator 更新为新磁盘内容并清除过期的已保存 Edits；若用户有未保存编辑，Plannotator 警告并请用户在缓冲区与磁盘版本之间选择。

## 后果

源文档探测必须区分 `ok`、`missing` 和 `unavailable` 结果。实时磁盘协调必须显式处理缺失文件，而不是将其视为 null 快照。

源保存端点必须允许在相同路径安全重建先前打开的源文件。UI 必须显示简单的缺失文件警告，同时保留编辑器文本。

这保持了熟悉的行为并避免过度构建的恢复 UI，但意味着保存路径现在负责先前打开文件的安全重建。

测试应覆盖缺失与不可用读取、为缺失的原文件清除或标记已保存 Edits 为过期，以及将缺失的源文件保存回磁盘。
