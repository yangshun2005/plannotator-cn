# 003. PR 上下文实时更新

日期：2026-06-30

## 状态

已接受

## 背景

PR 概览现在在一个面板中显示描述、评论、审查线程、检查和合并状态。ADR 002 增加了热 PR 上下文缓存，使这些数据在服务器启动和切换 PR 时开始加载，`/api/pr-context` 可以等待已启动的工作。

该缓存仍是一次性会话缓存。如果用户在审查 PR 期间评论或检查发生变化，UI 不会自动更新。用户也不想手动刷新。

审查应用已使用 SSE 处理实时本地数据，例如外部注释和代理任务。提供方读取通过用户已认证的 `gh` 或 `glab` CLI 处理，因此提供方流量必须集中在服务器中，不能随浏览器标签页数量倍增。

正常速率限制使自动刷新可行。一个被监视的 GitHub PR 每 30 秒刷新一次，远低于单次审查会话的普通已认证 GitHub 主限制。一个被监视的 GitLab MR 每 30 秒刷新一次，也远低于 GitLab.com 普通使用的已认证 API 限制。现实风险场景包括：大量打开的 PR 会话、异常昂贵的 GitHub GraphQL 查询、其他工具共享同一令牌，以及大量 GitLab 评论写入突发。

## 决策

将 PR 上下文设为服务器拥有的实时缓存。

两个审查服务器实现都将为每个 PR URL 保留一个缓存条目。每个条目将跟踪最新上下文、最新错误、版本、进行中的刷新、监视者数量、刷新定时器，以及速率限制导致的任何冷却。

服务器将继续在启动和切换 PR 时预热 PR 上下文，不阻塞这些流程。

客户端将在 PR 模式下通过新的 SSE 端点自动订阅 PR 上下文更新：

```text
GET /api/pr-context/stream
```

服务器将每 30 秒刷新被监视的 PR 上下文。每个 PR URL 刷新一次，而不是每个标签页一次，并且当一次刷新已在进行中时，绝不再启动第二次刷新。

当某个 PR URL 的最后一个监视者断开连接时，服务器将停止该 PR 的循环刷新定时器。最后一次成功的值可以保留在审查会话的缓存中。

在 `/api/pr-action` 成功发布审查或评论后，服务器将立即刷新目标 PR 上下文并广播结果。

`GET /api/pr-context` 将保持兼容，并继续在成功时返回原始 `PRContext`。它可以继续作为初始快照路径，以及 SSE 不可用时的轮询回退。

如果 GitHub 或 GitLab 返回速率限制错误，服务器将在可用时保持最后一次成功的上下文可见，在流状态中将上下文标记为过期/错误，等待提供方重试时间或保守冷却，然后自动重试。

提供方适配器必须将失败的主上下文读取暴露为刷新错误。当提供方命令失败时，它们不得将空白上下文作为成功更新广播。

此决策尚未实现完整的双向评论。它创建了所需的基础：一个服务器拥有的远程上下文视图、写入后立即协调，以及未来表示待处理、已发布、失败和已同步评论状态的天然位置。

## 后果

用户应无需手动刷新 PR 概览即可看到新评论、变更的检查，或通过 Plannotator 发布的评论结果。

提供方读取保持有界，因为服务器每个被监视的 PR URL 刷新一次，并在标签页之间共享结果。

审查 UI 在 PR 模式下增加一个额外的本地 SSE 流。这在当前应用中可以接受，但未来的实时审查功能应避免添加许多单独的流。如果流数量成为问题，PR 上下文事件可以合并到更广泛的审查事件流中。

实现必须更新两个服务器运行时和共享的审查客户端 Hook。

实时刷新循环必须处理提供方错误，不清除有用的缓存数据，也不强制手动重试。

未来的双向评论应基于此缓存构建，添加提供方特定的写入端点、乐观的待处理本地评论、提供方 ID 协调，以及在支持时执行回复和解决等线程操作。
