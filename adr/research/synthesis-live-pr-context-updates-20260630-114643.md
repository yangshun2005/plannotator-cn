# 综合：实时 PR 上下文更新

日期：2026-06-30

## 摘要

正确的模型是服务端负责新鲜度。浏览器不应决定何时调用 GitHub 或 GitLab，多个标签页也不应成倍增加提供商流量。服务端应为每个 PR URL 维护一个实时 PR 上下文缓存条目，并向 UI 发布更新。

现有的热缓存是良好基础。它已让启动和 PR 切换时提前开始提供商请求，并与 `/api/pr-context` 共享进行中的 Promise。下一步是把这种一次性 Promise 缓存改为带最新值、刷新循环、版本号和订阅者的实时缓存。

## 推荐行为

启动和 PR 切换时拉取一次，已实现。

PR 模式的浏览器标签页打开时，自动订阅 PR 上下文更新。流应发送即时快照（若存在），或发送加载状态（若刷新进行中）。

按固定间隔刷新被监视的 PR。初始默认 30 秒。

每个 PR URL 只刷新一次。同一 PR 打开三个标签页时，它们都从一次服务端刷新收到相同结果。

Plannotator 通过 `/api/pr-action` 发布评审或评论后，立即刷新该 PR 并广播结果。

无人监视 PR 时，停止循环定时器。在会话缓存中保留最后一次成功的值。

提供商失败时，若有最后一次成功的值则继续显示，在流中包含错误/过期状态，并自动重试。若错误是限流响应，等待后再重试。

## 为何采用此形态

这给用户期望的体验：无需手动刷新。PR 打开期间，新评论、评审状态和检查会自动出现。

避免浪费。提供商读取集中在服务端，浏览器标签页只监视本地状态。

保持低限流风险。30 秒间隔下，一个被监视的 GitHub PR 每小时约刷新 120 次。一个被监视的 GitLab MR 每分钟约 10 到 12 次 API 请求。对正常认证用户而言是可行的。

契合现有应用。评审 UI 已使用 SSE 获取实时数据，流失败时回退到轮询。

也为双向评论奠定基础。一旦服务端拥有实时上下文，写操作可乐观添加待处理的本地条目、发送提供商写入、刷新远程上下文，并按提供商 ID 对账。

## 应避免

不要让每个浏览器标签页独立轮询 GitHub 或 GitLab。

不要为摘要、评论、检查、评审线程和合并状态创建独立的流。

所有浏览器标签页关闭后不要永远刷新。

不要让提供商限流处理依赖复杂的活动猜测。使用简单的生命周期事实：被监视即刷新，未被监视即停止，写入即立即刷新，提供商说慢就慢。

不要破坏现有 `/api/pr-context` 快照响应。保持其返回原始 `PRContext` 以兼容。

## 实现方向

在两个评审服务器中添加共享的实时上下文管理器形态，或在保持简单的前提下将核心状态机移入共享代码。主服务器和 Pi 服务器仍需运行时特定的 HTTP/SSE 胶水。

缓存条目应跟踪：

- `url`
- `ref`
- 最新 `context`
- 最新 `error`
- `version`
- `inflight`
- `watchers`
- 刷新定时器
- `nextAllowedRefreshAt`

事件应为小型 JSON 信封：

- `snapshot`
- `updated`
- `loading`
- `error`

现有 `usePRContext` Hook 应变为实时客户端 Hook。可保持当前返回形态，面板无需大改。

轮询回退可按相同间隔调用 `/api/pr-context`。服务端缓存仍确保这不会为每个标签页创建一次提供商刷新。
