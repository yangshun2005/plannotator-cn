## 决策

累积的物理设备评审已足够。不要让评审者重复 Phase 1B 的 composer 检查清单。Safari 阶段失败是阻塞性缺陷，最终 iPhone 通过确认了其修复。

工作按以下顺序推进：

1. **Phase 1C — 共享触摸与对话框契约。** 完成小型、按能力门控的基础，不重排任一产品界面。
2. **Phase 2A — 移动端 Code Review 外壳与到达。** 用单一主手机界面和临时次级导航/上下文替换压缩的桌面组合。
3. **Phase 2B — 移动端 Plan 外壳与导航。** 减少常驻 Plan 界面元素，恢复被阻塞的文件夹/多文件路径，稳定编辑与完成控件。
4. **Phase 3 — 触摸选择与标注语义。** 原型并验证多块 Plan 选择和多行 Pierre 选择作为专用交互。

此顺序不只是产品重要性的排序。它先分离共享机械安全与信息架构，再分离布局与更难的选择语义。这样每个评审门禁都易于理解，并防止手机变通方案改动桌面偏好。

## 已纳入的 Phase 2B 物理反馈

首次 2B.1 手机通过表明，仅恢复文件夹导航不够：选中文件后，Plan 仍暴露其整个桌面标注矩阵以及 Wide / Focus / Edit 微链接。评审者还要求 Plan 完成决策遵循 Code Review 模式并移入 Options。

此反馈分配给 2B.2，并实现为单一紧凑文档界面契约：

- 到达时显示一个 `Annotate · <method>` 入口，而非 Markup / Comment / Redline / Label 旁的 Select / Pinpoint；
- 紧凑定位始终通过 Markup 语义呈现，Select 文本和 Pinpoint 是仅有的前置获取选择；
- 紧凑方法选择仅限会话，保护桌面偏好；
- Wide 和 Focus 完全从紧凑触摸中移除；
- Edit 移入 Options，激活时获得正常流的 Save / Done / Cancel 行；以及
- 终端决策移入 Options，同时调用完全相同的现有处理程序和警告路径。

此清理不声称任何 Phase 3 多块或多行选择语义。Pinpoint 单块定位和原生拖拽选择仍是 2B.2 物理门禁的已知输入基础。

下一次 iPhone 文件夹通过暴露了 2B.1 内的一个状态转换缺陷：文件选择关闭导航器，然后异步链接文档激活重放桌面“打开文件侧边栏”行为并复活紧凑导航器。该关闭/重开序列导致可见闪烁，并迫使评审者在看到选中文档前使用 X。紧凑激活现抑制该仅桌面副作用；选中文件名和文档渲染时导航器保持关闭，而精细指针桌面保留其现有侧边栏激活。

## 立即下一实现：Phase 1C

### 成果

共享按钮和共享对话框关闭控件物理上可安全触摸，共享对话框在可见 Safari 视口内保持可达，精细指针桌面几何不变。

### 范围内

- 引入共享 `--pn-touch-target` 令牌和 `data-pn-touch-target` 标记。
- 对两个现有共享按钮原语和共享对话框关闭控件应用粗指针 44×44 最小命中区域。
- 将共享对话框原语限制在 1A/1B 建立的可见视口和安全区域契约内。
- 在触及的原语中，将仅悬停效果门控到支持悬停的精细指针。
- 提供即时、克制的按压反馈和减少动态路径。
- 仅转换证明契约所需的代表性共享对话框。
- 验证 iPhone 和 iPad 几何，包括混合 iPad 触摸加指针。

### 明确范围外

- 不大规模扩展每个手写 Plan 或 Review 工具栏控件。
- 不重设计 Plan 工具条、底部操作栏或移动导航。
- 不更改 Code Review 面板、Dockview、页头、Guide 或 diff 组合。
- 不基于视口写入 Split/Unified 偏好。
- 不更改 Pierre、`DiffViewer`、行选择或建议编辑。
- 不新增 sheet 系统或视觉语言。

### 实现接缝

预期源边界保持：

- `packages/ui/theme.css`
- `packages/ui/components/ui/button.tsx`
- `packages/ui/components/core/button.tsx`
- `packages/ui/components/ui/dialog.tsx`
- 聚焦组件和几何测试

如果正确的 44 px 目标破坏密集手写行，记录到其界面阶段，而非引入未记录的紧凑例外。

### 下一次联合评审门禁

检查点满足以下条件时可供评审：

- 代表性按钮和对话框关闭命中框在粗指针上至少 44×44 且不重叠；
- 共享对话框在 320×568、390×844 和键盘缩减高度下，关闭控件和主操作保持可达；

### Phase 1C 实现检查点

实现已在 `codex/mobile-phase-1c-touch-dialog` 完成，准备进行上述简短物理设备门禁。共享契约现在：

## Phase 2A 预览：移动端 Code Review 外壳与到达

Phase 2A 是第一个结构重设计。其职责是让评审产物，而非桌面工作区，拥有手机视口。

### 固定原则

- 手机上一次一个主全宽界面。
- Tree 仍是最佳新用户桌面默认，绝不被移动端呈现决策覆盖。
- 文件导航、PR 上下文、标注、AI 和代理成为临时手机界面，而非挤压 diff 的 flex 兄弟。
- 空 PR 区域不渲染结构仅为了宣告缺失。
- 手机页头暴露位置、导航和一个上下文操作；仅桌面控件移至渐进披露之后。
- 手机友好的 Unified 呈现可以是会话/设备覆盖，但不得重写用户的桌面 Split 偏好。
- Guide 和所有文件是观察到的两个最强移动起点。入口决策应通过工作原型和物理评审做出，而非从响应式截图假设。

### Phase 2A 评审门禁

实现被接受前，评审者将使用同一 GitHub PR 比较至少两个工作手机组合：

1. 产物优先的所有文件 / Unified 到达；
2. Guide 优先到达，带直达原始 diff 的路径。

所选组合必须保留桌面行为，使文件/PR 上下文可达而不缩窄产物，保持目标决策完全可见，并支持完整的单行评论和批准/发送旅程。多行触摸选择明确在 Phase 3 评估，不作为外壳门禁。

### Phase 2A 实现检查点

首次实现已在 `codex-mobile-phase-2a-review-shell` 完成。初始物理 iPhone 通过未通过阶段门禁：它确认了产物优先方向，但暴露了响应式 Chromium 无法复现的 review 界面元素和 Safari 阶段问题。迭代保留相同产物优先选项，同时保持现有引导式 Review 接管可从紧凑 Options 菜单直接到达，以便两个候选阅读组合可针对同一 review 比较。

紧凑外壳仅在视口宽度至多 1024 px 且设备暴露粗指针时激活。窄精细指针桌面窗口保留桌面工作区。在紧凑外壳内：

- PR 和本地 review 以全宽所有文件到达，而非在 diff 旁打开树或 PR 概览；
- Unified 是初始会话呈现，但在手机上更改仅限会话，绝不写入保存的桌面 Split/Unified 偏好；
- Git 状态、Tree、提交、PR 上下文和文件导航占据一个全舞台临时导航器，选择目标后关闭；
- 标注、AI 和 Review Agents 占据单独的全舞台临时界面，而非成为固定 flex 兄弟；
- 页头是一个 52 px 三列行：导航、几何居中的 review 位置和 Options。目标、退出、发送/发布、批准、Guide 和次级工具移入该菜单，而非争夺手机宽度；
- 33 px dock 条仅在紧凑触摸上包含标签。其先前 44 px 齿轮目标物理上溢出条进入第一个文件页头；
- 紧凑文件页头是 44 px 行，仅包含折叠、路径、状态和变更计数。已查看、Git Add、语义/调用流徽章、实验性 Edit 和应用内打开保留为桌面操作，而非移动文件界面元素；
- 目标 coachmark 不在紧凑触摸上挂载，因为其目标决策现在直接位于 Options；
- 平台提交对话框使用共享可见视口 Dialog，到达时不抬起软件键盘，撰写文本保持 16 px，滚动长恢复详情，并固定其终端操作；以及
- 展开的 review composer 空闲时上限 28 rem，仅按可见键盘视口需要扩展，而非在撰写开始前覆盖整个手机；
- 原始 diff 保留 Pierre 的有界嵌套滚动视口。实现了仅紧凑的页面滚动代理，然后在物理 iPhone 通过期间拒绝：文档前进而 Pierre 虚拟窗口停止，留下冻结 diff 后跟大空白区域，且粘性 review 舞台保留不透明 Safari 顶部扩展。代理立即移除以恢复可靠文件滚动。虚拟化 review 的 Safari 界面收缩仍是开放设计工作，而非已交付声明；以及
- PR 概览使用 Summary/Comments 作为互斥紧凑区域。空讨论完全不渲染 Comments 区域。最后一项移除还故意通过消除空结构面板改善桌面。

未更改任何 Pierre 库源、行映射、触摸范围选择、建议编辑器、服务器、Tailscale 或持久化桌面面板默认代码。所有文件集成提供仅紧凑的 44 px 页头度量，而其现有嵌套 CodeView 滚动器仍是真相来源。Tree 仍是桌面首次使用默认。

自动证明包括紧凑触摸检测器和监听器清理、仅会话 diff 样式路由、可见视口目标/提交界面、精确 PR 讨论包含规则、空桌面讨论和单区域紧凑 PR 上下文。生产 Review 构建、共享类型检查、聚焦 DOM 测试和 diff 空白检查通过。

渲染预检覆盖 320×568 和 390×844 手机舞台、820×1180 平板舞台和 1280×720 精细指针桌面控制。紧凑页头保持 52 px，两个临时界面恰好占据剩余应用舞台，文件选择关闭导航，未测量到页面宽度溢出。桌面控制保留其 37 px 页头和 256 px 文件树。浏览器预检无法关闭真实触摸、Safari 界面、tailnet PR 或混合 iPad 门禁；这些仍是评审者的验收通过。

#### 物理评审脚本

通过 Tailscale 在 iPhone 上打开同一 GitHub PR，然后 iPad（如可用）：

1. 确认到达是所有文件、全宽和 Unified；树和 PR 面板不得已打开。连续滚动多个文件。不得有冻结虚拟窗口、大空白尾部、跳回开头或触摸滚动丢失。Safari 顶部界面和不透明扩展是下一设计迭代的记录开放阻塞，而非此回滚检查的通过条件。
2. 确认手机页头仅包含 Review 导航、居中的 review 位置和 Options。打开 Options 并验证目标、退出、发送/发布（存在反馈时）和批准可在那里到达。
3. 确认 dock 标签行没有齿轮/折叠簇重叠第一个文件。紧凑文件页头应仅显示折叠、路径、状态和变更计数——无应用内打开下拉或桌面徽章/操作。
4. 打开 Review 导航，在文件、所有文件和 PR 概览之间移动，确认每个选择返回全宽主界面。
5. 在 PR 概览中，确认空讨论没有 Comments 控件；存在讨论时，在 Summary 和 Comments 之间切换而不分割屏幕。
6. 打开 Options → 引导式 Review，阅读一章，然后返回原始 diff。
7. 从 Options 打开标注（以及 AI/Agents 如可用），确认界面替换而非挤压 diff，然后关闭。
8. 选择一行代码并打开评论。聚焦 textarea
