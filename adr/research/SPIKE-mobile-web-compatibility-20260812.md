# SPIKE：计划、文档与代码审查的移动端 Web 兼容性

日期：2026-08-12
状态：研究综合，非产品规格
基线：`origin/main` / `ef49c701c23b867cec2a5d78343813ba89d2a025`（`v0.27.1`）

方法：双智能体（A：独立设计与可用性评估 · B：独立检测器与浏览器证据评估）

## 问题

在 Plannotator 现有 Web 界面成为 iPhone 和 iPad 上出色的触控优先体验之前——尤其是通过 Tailscale 访问会话时——它必须学习、保留、移除和重新设计什么？

本 SPIKE 有意止步于正式设计规格之前。它建立可复用的审计方法、有源码和浏览器支撑的清单、有前景的产品方向，以及指定实现前必须做出的决策。

## 核心发现

Tailscale 解决的是可达性，不是移动性。它暴露的是 Plannotator 本地提供的同一批单文件 React 应用；不会选择替代的移动端渲染器或路由。因此移动端机会是产品外壳与交互设计问题，不是 Tailscale 渲染问题。

当前界面分为三个不同的就绪等级：

1. **计划/文档阅读在视觉上响应式，但尚未触控优先。** 产物仍可读，页面级横向溢出受控。但界面元素密集，多数控件高 17–28 px，触控设备会展开每个工具条标签，标注/编辑的完成操作易受 Safari 视口和键盘行为影响。
2. **代码审查是把桌面布局压缩进窄视口。** 在 390 px 下，默认 256 px 文件树只给 Pierre 留下 134 px。打开固定 288 px 审查侧栏后只剩 102 px。隐藏文件树并选择 Unified 证明 diff 在手机宽度下可用；失败的是默认布局。
3. **Guided Review 是现有最强的移动端产品原语。** 它已把变更集转化为有序的叙事阅读流，隐藏文件树，在手机宽度下堆叠章节，并复用真实的 Pierre diff。它需要移动端外壳和触控处理，而非概念替换。

最严重的兼容性问题不是视觉问题：多文件/文件夹标注在 `lg` 以下被阻断。文件夹空状态提示审查者从侧栏选择文件，但在这些宽度下，折叠的侧栏标签和展开的侧栏都被隐藏。

推荐的研究方向是**产物优先、一次一个阶段的外壳**：

- 手机：一次一个主界面；全宽文档或 Unified diff；导航和标注放在 sheet 中；高风险操作放在刻意设计、拇指可达的审查栏中。
- iPad 竖屏/触控：一个产物加至多一个临时伴随界面；不要仅凭宽度打开桌面侧栏。
- iPad 横屏配指针/键盘：在可用中央画布仍足够大时，保留强大的桌面工作区。

## 范围与非目标

### 范围内

- 计划审查和文档标注，包括文件夹、版本、关联文档、原始 HTML、直接编辑和标注面板状态。
- 代码审查，包括 Git 状态 / Tree / Commits、全文件和单文件 Pierre diff、暂存/已查看/文件评论、右侧栏和 Guided Review。
- iPhone 竖屏和横屏；iPad 竖屏和横屏；触控优先和指针辅助的 iPad 场景。
- 响应式布局、触控目标、手势/直接性、视觉噪音、层级、排版、安全区域、动态视口、虚拟键盘、无障碍、中断/恢复和移动端载荷成本。
- 本地和 Tailscale 发布的会话如何提供同一前端。

### 范围外

- 实现响应式 CSS 或组件。
- 选择最终断点、视觉稿、手势或导航标签。
- 更改 Pierre 集成行为。
- 修改 Tailscale Serve 映射或测试真实 tailnet。
- 声称观察到物理 Mobile Safari、VoiceOver、刘海、Home 指示条或键盘行为；这些需要物理设备验证。
- 重建共享 UI。任何最终实现都必须演进 `@plannotator/ui` 接缝和现有应用。

## 研究方法

本方法旨在复用于后续移动端设计迭代和回归审计。

### 1. 冻结产品基线

- 检查行为前，获取并比较 `HEAD` 与 `origin/main`。
- 在每个产物中记录确切提交和版本。
- 排除一次性或历史分支，除非特定当前行为指向它们。
- 保留工作树；本轮不做产品代码更改。

### 2. 判断响应式前先映射可达性

对每个用户入口，记录：

- 调用方式和运行时；
- 绑定地址和通告 URL；
- 提供的 HTML 资源；
- 会话是本地、远程、共享静态还是 tailnet 发布；
- 移动用户能否到达该流程。

这避免把传输工作与响应式行为混淆。

### 3. 审计旅程，而非仅屏幕

每个界面都按同一旅程评估：

1. 到达并定位。
2. 找到产物或变更文件。
3. 阅读并理解。
4. 选择或指向证据。
5. 编写、编辑或删除反馈。
6. 审查累积反馈。
7. 批准、发送、关闭或恢复。
8. 中断或旋转后返回。

代码审查额外加入暂存、已查看状态、文件导航、diff 模式、Guide 导航和平台/智能体目标。文档标注额外加入文件夹/文件选择、版本、关联文档、直接编辑和原始 HTML。

### 4. 使用设备与输入矩阵

最低渲染矩阵：

| 类别 | 参考视口 | 输入场景 | 目的 |
|---|---:|---|---|
| 紧凑手机竖屏 | 320×568 | 触控 | 最小现实布局压力 |
| 当前手机竖屏 | 390×844 | 触控 | 主要单手审计 |
| 手机横屏 | 844×390 | 触控 | 刘海/安全边缘和垂直压缩 |
| iPad 竖屏 | 768/820/834×1024–1194 | 触控 | 断点和侧栏压力 |
| iPad 横屏 | 1180×820 | 触控或指针 | 多窗格可行性 |
| 桌面对照 | ≥1280 宽 | 指针 + 键盘 | 保留现有优势 |

响应式 Chromium 确定布局和计算几何。物理设备轮次后续必须覆盖 Mobile Safari、`pointer: coarse`、`hover: none`、动态浏览器界面、软键盘、选择手柄、旋转、VoiceOver、减弱动态效果、增强对比度和 Tailscale 延迟。

### 5. 区分证据与推断

每个发现使用一个或多个证据标签：

- **已观察** — 在渲染视口中复现。
- **已测量** — DOM 矩形、计算样式、载荷或控制台结果。
- **源码确认** — 实现确立了该行为。
- **平台风险** — 源码与已知移动浏览器行为冲突，但仍需物理设备复现。
- **设计假设** — 待原型验证的候选方向；不是需求。

不要把平台风险或设计假设升级为已观察缺陷。

### 6. 通过五个视角评估

1. **实用性：** 审查者能否完成核心任务？
2. **层级/噪音：** 界面元素是否压过产物？
3. **直接性：** 触控是否作用于可见对象，并给出即时、可中断的反馈？
4. **兼容性/无障碍：** 44×44 目标、16 px 聚焦文本输入、安全区域、动态视口、非悬停访问、语义、焦点、对比度、减弱动态效果。
5. **性能/韧性：** 初始 HTML 成本、解析/高亮工作、虚拟化、加载反馈、重连、草稿和恢复。

Apple 设计视角贡献了物理直接性、单阶段聚焦、拇指可达、sheet、可中断性和尊重系统惯例。设计工程视角贡献了目标尺寸、Safari 输入/视口规则、输入能力检测、减弱动态效果和性能纪律。批评框架贡献了 Nielsen、认知负荷、人物角色、检测器和证据存储检查。

### 7. 独立评分严重性和置信度

| 优先级 | 含义 |
|---|---|
| P0 | 受支持的移动旅程无法完成。 |
| P1 | 核心审查或反馈不可用、不可靠或危险地易错。 |
| P2 | 实质性摩擦、噪音、无障碍风险或可避免的低效。 |
| P3 | 打磨、一致性或未来适应性问题。 |

当渲染证据与源码一致时置信度为高，源码支撑的平台风险为中，未测试概念或罕见场景为低。

### 8. 运行两项隔离评估

- 评估 A 在不看检测器输出的情况下判断设计质量、Nielsen 启发式、认知负荷、情感旅程和人物角色。
- 评估 B 运行一次确定性检测器，分诊误报，收集浏览器几何、计算样式、截图和控制台证据，且不看 A。
- 仅在 A 完成后开始综合，然后调和 B。

这防止自动化模式警告锚定设计审查。

### 9. 规格前应用决策门

在产品决定以下事项前，不要编写正式移动端规格：

- 手机意图：深度检查、分诊，还是两者兼有；
- Guide 是默认移动路由还是可选路由；
- 批准/操作的位置和保障措施；
- 宽度加输入的适配策略；
- 最低支持设备/浏览器矩阵；
- 通过 tailnet 可接受的首次加载预算；
- 文件夹和多文档导航在移动端如何呈现。

## 前端如何提供

### 构建与渲染模型

- 计划/文档应用是 `packages/editor/App.tsx`，由 `packages/ui` 的共享组件和 token 组合。
- 审查应用是 `packages/review-editor/App.tsx`，同样使用 `packages/ui`、Dockview 和 `@pierre/diffs`。
- Vite 和 `vite-plugin-singlefile` 将 JavaScript、CSS、字体/资源以及 Pierre 高亮 worker 内联到每个应用的一个 HTML 文件中。
- Bun 服务器将这些 HTML 字符串保存在内存中，并作为非 API 路由的 SPA 响应返回。
- 浏览器随后从同源 `/api/*` 路由获取会话数据和变更。Tailscale 不改变此 API 或渲染契约。

相关源码：

- `apps/hook/vite.config.ts`
- `apps/review/vite.config.ts`
- `packages/server/index.ts`
- `packages/server/annotate.ts`
- `packages/server/review.ts`

### Tailscale 路径

编译后的 Bun CLI 为 `review`、`annotate`、`annotate-last` 和 `last` 支持 `--tailscale`。

1. Plannotator 强制本地模式，将 Bun 服务器绑定到 `127.0.0.1` 的随机或配置端口。
2. 它检查 `tailscale serve status --json`，拒绝抢占该端口已有的映射。
3. 它运行 `tailscale serve --bg --https=<port> http://127.0.0.1:<port>`。
4. Tailscale 终止 HTTPS 并代理完全相同的本地 Web 应用和 API。
5. Plannotator 通告 tailnet URL 和终端二维码，跳过本地浏览器打开，并在正常退出/信号时移除映射。

tailnet 会话对允许的对等节点私有，但没有 Plannotator 登录或每请求认证。任何能到达主机的对等节点都可使用会话 UI 和本地 API。因此标注智能体终端默认禁用。

重要旅程限制：智能体计划 Hook 不会自动添加 `--tailscale`，普通计划 Hook 命令也不是受支持的 `--tailscale` 子命令。tailnet 计划门目前使用直接标注调用，例如 `plannotator annotate path/to/plan.md --tailscale --gate`。

已发布的文档于 2026-08-12 检查：`https://docs.plannotator.ai/open-source/tailscale`。

### 渲染场景矩阵

| 场景 | 前端 | 可达性 | 移动端影响 |
|---|---|---|---|
| Claude/Gemini 计划 Hook | 计划/编辑器 HTML | 默认本地浏览器 | 现有自动计划流不会因该标志而 tailnet 发布 |
| `annotate --tailscale` | 标注模式下的计划/编辑器 HTML | Tailscale Serve HTTPS | 主要移动文档/计划路径；文件夹、HTML、版本、编辑和门变体都重要 |
| `review --tailscale` | 审查编辑器 HTML | Tailscale Serve HTTPS | 完整代码审查工作区原样到达手机 |
| SSH/远程模式 | 相同 HTML | 宽绑定 / 通告 HTTP 主机 | 安全上下文行为不同；响应式不变 |
| 共享静态链接 | 独立的静态/共享渲染路径 | 公共/共享服务 | 不是本审计的主要实时会话契约 |
| VS Code/Glimpse | 宿主窗口中的相同核心界面 | 本地宿主集成 | 不是手机目标，但共享 UI 更改必须保留它 |

## 已经强大的部分

### 计划/文档界面

- 产物具有独特的编辑身份，而非通用仪表盘样式。
- 阅读器内边距在手机宽度下收缩，在 390 或 834 px 下未观察到文档级横向溢出。
- 物理 iPhone 轮次确认，一旦关闭辅助侧栏和设置界面，计划本身阅读良好。
- 代码和表格保持自己的横向滚动，而不是加宽整个页面。
- 标注评论、草稿恢复、版本比较、直接编辑、链接、附件和主题化 markdown 都是领域特定且有价值的。
- 计划标注面板在 768 px 以下已变为固定全宽覆盖层。这是审查侧界面现有最佳模式。
- 原生移动文本选择在 `useAnnotationHighlighter.ts` 中有带防抖的粗指针 `selectionchange` 桥接。
- 存在减弱动态效果处理和色盲主题，尽管覆盖不均。

### 代码审查界面

- Git 状态 / Tree / Commits 和 since-base 组合是真实审查工作特有的。
- Pierre 为单文件和虚拟化全文件/Guide 视图集成一次；隐藏文件树并选择 Unified 产生了可行的手机宽度画布。
- 物理 iPhone 轮次发现初始 Review 设置对话框可接受，Guided Review 作为移动理解界面立即有前景。
- 同一轮次发现“Edit code to suggest”对话框可接受，All Files 视图视觉干净，为后续移动工作提供了两个具体可保留的组合。
- 文件暂存/已查看/评论状态和失败恢复复杂且可信。
- 首次运行审查设置对话框重排为单列手机布局，并保留明显的完成操作。
- iPad 横屏 1180×820 保留了强大可用的多窗格审查工作区。

### Guided Review

- 接管模式使变更集作为章节可理解，而不是先要求文件树定位。
- 在手机宽度下，章节堆叠为叙事后接真实 diff。
- 它使用相同的 diff、标注、暂存/已查看操作和虚拟化 CodeView，而不是产生脱节的摘要。
- 其“核心优先，胶水后置”排序直接降低移动端认知负荷。

### 韧性

- 草稿持久化、批准警告、部分平台发布恢复、重试收窄和显式错误状态强于典型开发者工具。
- 渐进披露已在反馈存在前隐藏 Send Feedback / Post Comments。

## 认知负荷评估

八项检查中五项在手机上明显失败：

- **单一焦点：** 失败 — 文件树、dock、diff、工具栏和侧栏共存。
- **分块：** 混合 — 标注模式已分组，但同时暴露太多组。
- **分组：** 通过 — 边框、表面、状态颜色和面板归属总体连贯。
- **视觉层级：** 失败 — 固定导航侧栏可能比产物占用更多宽度。
- **一次一件事：** 失败 — 外壳允许手机上文件树 + 分屏 diff + 右侧栏。
- **最少选择：** 失败 — 六种标注模式和许多审查控件先于主任务。
- **工作记忆：** 失败 — 仅图标操作和悬停帮助需要记住含义。
- **渐进披露：** 混合 — 提交操作是渐进的，但工作区外壳不是。
