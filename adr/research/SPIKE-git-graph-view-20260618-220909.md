# SPIKE：代码审查应用中的 Git 图谱视图

日期：2026-06-18
状态：**已积压** — 已探索，暂不构建。

## 我们探索了什么

想法：在审查应用中增加 Git 图谱视图。显示提交图谱；点击某个提交，其文件变更在右侧加载 — 本质上介于全文件视图与在不同提交的 diff 之间切换的功能之间。

这是一份研究笔记，不是承诺。我们暂时搁置。

## 关键发现：diff 查看器已与数据来源无关

`App.tsx` 请求 `/api/diff` → 得到 `rawPatch` 字符串 → `parseDiffToFiles()` → 提供给 FileTree + 全文件视图 + 单文件视图。查看器不关心 patch 来自哪里。因此“点击提交 → 查看其文件” = 获取该提交的 patch 并送入同一流水线。

**Pierre diff 查看器几乎无需改动。** 这是主要的担忧点，而它基本上零成本。

## 已可复用的部分

- `runGitDiff`（packages/shared/review-core.ts）已支持多种 diff 模式：未提交 / 已暂存 / 上次提交 / merge-base / 全部 / 分支。`last-commit` 实际上就是 `git diff HEAD~1..HEAD` — 因此单个提交的 diff（`git diff <sha>^..<sha>`）只是一个小新增模式。
- `listRecentCommits()`（review-core.ts 约 245 行）已运行一次 `git log --pretty` 并返回 `RecentCommit[]`（用于基础分支选择器）。这是提交列表的种子。
- `/api/diff/switch` 已能切换当前 diff 并重新渲染。选择提交在概念上是另一种切换。

## 全新需要做的部分

1. **按提交的 diff** — 扩展 diff 后端以接受 sha（`git show` / `git diff <sha>^..<sha>`）；上下文扩展的基准变为父提交。工作量小。必须在 Pi 服务端同步实现。
2. **图谱数据** — 在日志中加入父哈希（`%P`）+ 引用（`%D`），然后计算泳道布局（每个点/边位于哪一列）。DAG 解析很简单；泳道/轨道布局是繁琐的部分。
3. **图谱 UI** — 行 + SVG 轨道（点、彩色分支线）、提交元数据、选中、大仓库的虚拟化。这是工作量的主体。

## 真正的坑

diff 系统还支持 **jj 和 Perforce**，不只是 git。提交图谱是 git 特有的（jj 有自己的 log/op-log 模型）。因此除非以后增加 jj 变体，否则这将是 **仅限 git**。需事先决定。

## 建议的分阶段（如果/当我们接手时）

- **阶段 1 — 提交浏览器（小/中）：** 侧边栏中的扁平提交*列表* + 按提交的 diff 模式 + 点击加载到现有的全文件视图。无需改动查看器，后端少量新增。低成本验证工作流。
- **阶段 2 — 图谱（中，主要是前端）：** 在阶段 1 的数据 + 接线之上叠加泳道轨道 / 分支颜色。“酷炫可视化”在这里。

## 结论

非常可行。阶段 1 的工作量小得惊人，因为查看器是解耦的。暂时积压 — 有需求时再议，从阶段 1 开始。
