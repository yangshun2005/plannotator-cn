## 嵌套项目符号

### 两级 — 无序

- 顶层项目 A，文本足够长，在普通浏览器窗口的典型缩放级别下会换行显示
  - 嵌套在 A 下，描述也较长，以便确认项目符号固定在文本顶部，而不会漂移到整个项目的垂直中心
  - A 下的另一个嵌套项，同样冗长，使换行行为在手动测试中清晰可见
- 顶层项目 B，也有相当多的文本以确保换行，我们可以观察标记相对于其下方内容块的对齐方式
  - 嵌套在 B 下，附加细节：此项故意写得很长，即使在宽视口下项目符号对齐修复也显而易见

### 三级 — 无序

- 第一级 — 这是一个跨多行的长项目，以便验证顶部对齐修复在最外层嵌套级别也成立，而不仅仅是深层嵌套内容
  - 第二级 — 同样写了足够多的文字以触发换行，确认修复在所有缩进级别一致适用，而非一次性效果
    - 第三级 — 本节最深级别，散文足够长至少换行一次，使项目符号相对于第一行的位置清晰可观察
    - 另一个第三级项目，长度与上方类似，以便在最深层有两个连续的换行项目
  - 回到第二级，描述比之前更长，使此项也换行，我们可以发现同一嵌套深度下兄弟项之间的任何回归
- 另一个第一级项目，故意冗长以触发换行，为顶层对齐检查提供第二个数据点

### 有序与无序混合

1. 第一个有序项目，细节足够多以致超过一行，确认顶部对齐修复对有序标记和普通项目符号同样有效
   - 无序子项，描述足够长以致换行，我们可以看到项目符号位于换行内容的顶部，而非漂浮在中间
   - 另一个子项，同样冗长，以验证同一父项下兄弟项之间的一致对齐
2. 第二个有序项目，也足够长以致换行，为我们提供第二个有序标记来检查顶部对齐是否正确
   - 第二个有序项的子项，写得较长使项目符号换行，无需眯眼即可测试对齐
3. 第三个有序项目，以同样冗长的描述收尾，保持一致

### 有序嵌套

1. 第一阶段 — 准备工作，搭建环境、配置依赖，并建立所有后续阶段构建所基于的基线
   1. 任务 A 涉及研究当前实现并记录所有需要处理的边界情况，然后再继续推进
   2. 任务 B 涵盖编写解决方案的初稿，包括解释每个非显而易见决策背后理由的行内注释
2. 第二阶段 — 主要实现阶段，大部分工作在此发生，大部分代码库变更在此引入
   1. 任务 C 是核心重构，协调地触及解析器、查看器和列表标记组件，以避免回归
   2. 任务 D 是后续清理，移除死代码、更新测试，并确保变更后差异引擎仍产生正确输出
      1. 子任务 D1：更新解析器测试，覆盖重构期间新增的列表续行逻辑
      2. 子任务 D2：按正确顺序重建所有构建目标，并在合并前对测试夹具运行完整的手动冒烟测试

### 深层嵌套与复选框

- [ ] 顶层任务，描述较长会换行，以确认复选框图标保持在项目顶部，而非相对于所有文本行居中
  - [x] 已完成的子任务，写了额外细节，使选中状态和删除线样式在换行内容的多行中都可见
  - [ ] 仍待处理的子任务，也写得足够长以致换行，以便比较同一嵌套级别下选中与未选中项的视觉对齐
    - [ ] 最深级别的子子任务，足够长以致换行，确认即使在三层嵌套加复选框标记的情况下修复也成立
    - [x] 另一个已完成的子子任务，以便在此深度同时拥有选中和未选中的示例进行彻底的视觉比较
  - [ ] 第二级的另一个子任务，写得冗长以换行，完善此嵌套结构的对齐测试用例集
- [x] 另一个已完成的顶层任务，描述较长，使删除线和弱化文本样式在多行换行中可见

### 多行列表项（续行）

- 这是一个描述确实很长的列表项，延续多行。内容足够多，即使在宽屏上也至少应换行一次，为我们提供项目符号对齐修复在真实场景中的示例，而不依赖人为换行。
- 短项目。
- 另一个带续行的项目，也足够长以致在浏览器中自然换行，以便确认修复对续行式项目的适用方式与对单行长字符串项目相同。

### 带行内格式的项目符号

- 带 **粗体文本** 的项目，也足够长以致换行，以便确认即使第一行包含改变行视觉权重的粗体片段，项目符号也对齐到顶部
- 带 *斜体文本* 的项目，周围散文足够多以致换行，手动测试时项目符号相对于第一行的位置清晰可观察
- 在较长句子中间嵌入 `行内代码` 的项目，使项目换行，我们可以看到代码片段不会以任何意外方式影响项目符号对齐
- 在较长描述中嵌入 [plannotator.ai 链接](https://plannotator.ai) 的项目，该描述会换行，确认列表项内的锚点元素不会破坏顶部对齐行为
- 带 ~~删除线~~ 文本的项目，句子足够长以致换行，删除线样式在第一行可见，同时项目符号保持在顶部
- 句子中包含 ***粗斜体*** 组合强调的项目，句子足够长以致换行，为我们提供组合格式用例来检查对齐
- **粗体标签：** 粗体标签后的较长描述，故意冗长使项目换行，我们可以看到粗体标记正确位于块顶部

### 带行内格式的嵌套项目符号

- **阶段 1：** 初始设置 — 此阶段涵盖安装所有必需的运行时、验证环境，并确保团队中每位开发者都能在本地复现构建，无需额外配置步骤
  - 按照官方安装指南安装 `bun` 运行时；继续之前确认版本与 `.tool-versions` 或项目 README 中固定的版本一致
  - 在 monorepo 根目录运行 `bun install`，一次性拉取所有工作区依赖；冷缓存时可能需要一分钟，但后续运行会很快
  - 用 `bun --version` 验证安装的版本正确且与 CI 一致；此处不一致历史上曾导致难以诊断的微妙构建失败
- **阶段 2：** 配置 — 设置所有必需的环境变量，并确认本地服务器在尝试任何集成或端到端测试之前能干净启动
  - 设置 `PLANNOTATOR_PORT=19432`，以匹配 VS Code 扩展和 devcontainer 环境中使用的远程隧道配置所期望的端口
  - 在 devcontainer 内或通过 SSH 运行时导出 `PLANNOTATOR_REMOTE=1`；没有此标志，服务器会尝试在远程主机上打开浏览器，这将静默失败
  - 在运行任何依赖本地机器自动打开浏览器的测试之前，确认 SSH 隧道*已激活*并转发正确的端口
- **阶段 3：** 部署 — 按正确顺序构建所有目标，验证输出，并在打发布标签前通知团队，以便有时间发现任何最后一刻的问题
  - 从 monorepo 根目录运行 `bun run build`，它会先执行 review 构建，然后按正确顺序执行 hook 构建，避免过时的 HTML 被复制到 dist 文件夹
